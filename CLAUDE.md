# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development

`./dev.sh` (from repo root) is the canonical dev workflow. It:
1. Brings up Postgres via `docker/docker-compose.dev.yml` (exposed on host port **5431**, not 5432).
2. Runs the backend with `dotnet watch run` from `backend/`.
3. Runs the frontend with `npm run dev` from `frontend/`.
4. Traps Ctrl+C and tears all three down together.

Running components individually:

- Backend: `cd backend && dotnet watch run` — listens on `http://localhost:5132` (HTTPS profile also binds `7016`, see `backend/Properties/launchSettings.json`).
- Frontend: `cd frontend && npm run dev` — Vite default `http://localhost:5173`.
- Postgres only: `docker compose -f docker/docker-compose.dev.yml up -d`.

Frontend tooling (run from `frontend/`):
- `npm run build` — runs `tsc -b` then `vite build`.
- `npm run lint` — flat-config ESLint over `**/*.{ts,tsx}`.
- `npm run preview` — preview the production build.

Backend tests live in `backend.Tests/` (xunit + WebApplicationFactory against the in-memory provider). Run them with `dotnet test` from the repo root.

## Architecture

Three components, two compose files:

- `backend/` — ASP.NET Core Web API targeting **net10.0**, minimal hosting with `AddControllers()` / `MapControllers()`. DB connection comes from `ConnectionStrings:Default` (compose in prod, `appsettings.Development.json` in dev, pointing at port 5431).
- `frontend/` — React 19 + TypeScript + Vite + Tailwind, feature folders under `src/features` and route components under `src/pages`.
- `docker/` — two compose files:
  - `docker-compose.dev.yml`: Postgres only, port-mapped `5431:5432`, hardcoded creds (`jinsei/jinsei/jinsei`).
  - `docker-compose.yml`: full prod stack — Postgres + backend + frontend; reads creds from a root `.env` file (`POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`, see `.env.example`).

### Production request path (important)

In prod, the frontend container is an nginx serving the built SPA on port 80, published on the host as `127.0.0.1:8092` only. `frontend/nginx.conf` reverse-proxies `/api/` to `http://backend:8080` — **no trailing slash**, so the `/api` prefix is preserved. Controller routes therefore include it (`[Route("api/weight")]`).

TLS and exposure are handled outside the stack by `tailscale serve` on the host (`--https 9443 http://127.0.0.1:8092`); the app is reachable only from the tailnet. There is no Caddy, no public domain, no ACME.

The backend container exposes 8080 internally only (no host port mapping), so it is reachable from the frontend container by service name `backend` but not from the host.

### Dev vs. prod divergence to watch for

- **Dev Postgres port is 5431**, prod is the in-network default 5432 (service name `postgres`).
- Dev creds are hardcoded in `docker-compose.dev.yml`; prod creds come from `.env`.
- Dev backend connection string is **not** configured in `appsettings.Development.json` — anything DB-related needs to be added.
- The `/api` rewrite only exists in prod nginx. In dev, the frontend talks to the backend directly; if you add backend calls, configure a Vite dev proxy or use absolute URLs to `http://localhost:5132`.

## Domain notes

- **Workouts are read-only.** They are pulled from Hevy by `POST /api/workouts/sync` and identified by `(user_id, source, external_id)`, so a repeat sync updates rather than duplicates. The pull has a floor and a slot: `Hevy:SyncFrom` (2026-08-17) is the oldest day ever fetched — Hevy pages newest first, so the walk stops at the first session below the floor instead of reading pages it would throw away — and `HevySyncScheduler` pulls once on startup and then daily at `Hevy:SyncAtLocal` (19:30, in `Hevy:TimeZone`, recomputed against the wall clock so a container that was down over the slot does not drift). The floor governs loading, not deleting: sessions already in the log from before it stay. There is no exercise library, no routines and no live session tracking — those were removed deliberately; do not reintroduce a manual create path without being asked.
- **Sleep** is stored as durations — `time_in_bed_minutes`, `actual_sleep_minutes` — plus the optional clock times `bed_time` and `wake_time` as `TimeOnly`, which is what the regularity metric needs. Sending both times without a duration fills the duration in (wrapping over midnight); a duration that was sent explicitly always wins. The night is also stored in its phases — `awake_minutes`, `light_minutes`, `rem_minutes` (Sleep Cycle calls it "Traum"), `deep_minutes` — as four independent readings, never as shares. Light + REM + deep *is* the sleep, so `actual_sleep_minutes` is filled in from them when it was not sent; awake is time in bed, not sleep, and stays out of that sum, and so does `sleep_onset_minutes` ("Eingeschlafen nach"), which is stored beside them. Efficiency is derived on the way out and no longer shown anywhere; the API still returns it. Quality (the percentage Sleep Cycle reports) and the sleep-debt metric were both removed, column and all: one is a score that stopped being tracked, the other measured a backlog nobody acts on. Clock arithmetic on the client runs on a noon-anchored axis (`clockToNightAxis` in `lib/stats.ts`) so 23:50 and 00:10 are twenty minutes apart, and regularity is the spread of the sleep midpoint. Social jetlag (`socialJetlag`) is the shift of that midpoint between working days and free ones — the sleep literature's number for being woken by an alarm five days a week and by nothing on the other two. Both spreads are also shown as a score out of 100 (`consistencyScore`), the form every sleep tracker reports regularity in, with the minutes they were computed from kept underneath: the score is a convention, the minutes are the measurement, and nothing is built on top of the score. The phase shares are charted against the usual adult ranges — 13–23 % deep, 20–25 % REM — drawn as the goal line's tolerance band and labelled as a reference rather than a target.
- **Nutrition** is one row per day (calories, protein, carbs, fat, water, coffee, time of the last coffee), entered by hand or posted by the ingest endpoint. There is no food database and no external nutrition source. Fibre was tracked and then dropped, column and all; do not put it back without being asked.
- Sleep and nutrition are unique per `(user_id, date)` and written through upserts keyed on the date.
- **Charts and metrics.** There is one chart component (`frontend/src/components/charts/Chart.tsx`) covering lines, bars, stacked bars (`stack` on a series, for parts of one whole such as the phases of a night), the goal line and the trailing-average overlay. A chart of bars gives each day a slot and centres the bar in it, so the bars fill the width and only a gap separates the days; a chart with a line keeps the readings on the edges. Three dates sit on the x axis (first, middle, last) and the topmost grid label carries the unit. A tap reads the chart and the reading stays: only a mouse leaving clears it, and the card is placed in whichever half of the chart the finger is not on. Reading text is not selectable app-wide (`body` in `index.css`), or a long press on a tile pops the copy menu instead; inputs and the exported day text still are. Next to it, `StatTile`, `BarRow` and `MacroSplit` sit next to it, and `Sparkline` is a bare shape used on its own. A tile is a number and its name: the sparkline it used to carry said what the chart below it already said, and cost the number the width it then wrapped for. All the arithmetic — moving averages, regression slope, adherence, weekly buckets — lives in `frontend/src/lib/stats.ts` and is unit tested; components do not calculate. Series colours are the module colours from `lib/modules.ts`, never the accent. `MetricsPage` is a tab per area (`pages/metrics/sections/*`). Two switches, on purpose, and only one of them is on screen at a time: the header carries `PeriodTabs` (W/M/6M/J) on the overview, where the numbers are totals over a period, and `RangeTabs` + `useRange` (7/30/90/365 days) on every other tab, where they are series. Both are stored per key in localStorage.
- **Training analytics** come from `GET /api/workouts/analytics?days=` (`WorkoutAnalyticsService`), which parses `WorkoutLog.PayloadJson`: weekly load, sets per muscle group against the previous four weeks, and per-exercise progression with an Epley 1RM estimate (sets over 12 reps are ignored) plus a stagnation flag — a best older than four weeks on a lift still being trained. Muscle groups come from Hevy's exercise-template catalogue, cached for a day; sessions synced before that fall back to a coarse name match.
- **Habits across all habits** come from `GET /api/habits/overview?days=`: due vs. done per day and completion per weekday, which the per-habit streaks cannot answer.
- **Energy needs** are measured, never modelled (`backend/Services/EnergyService.cs`): mean intake against the weight-trend slope, which carries every cost a formula would have to guess at. It stays blank until 14 logged calorie days and 8 weigh-ins exist, and the card counts down to that instead of showing a bare dash. The arithmetic is on the server over one **fixed 28-day window**, served by `GET /api/energy/target`, because it used to run in the browser over whichever range the chart happened to be showing — the target moved when the range switch did. `frontend/src/lib/energy.ts` keeps only the pace presets and `KCAL_PER_KG`; the charts on that page still follow the range switch, the energy block does not. A Mifflin-St Jeor path with an activity factor was built and then removed — two numbers for one question left the reader deciding which to believe. `AppUser.birth_date`, `height_cm`, `sex` and `activity_level` survive from it, unused; do not wire them back into an estimate without being asked.
- **The week's calorie target** is derived, not typed: `weekly_rate_percent` on `AppUser` (0.35 gentle / 0.6 standard / 0.9 fast, chosen under Profile → Pace) times the **anchor weight** — the 7-day trend weight frozen at the current week's Monday (`AnchorWeight` in `EnergyService`). A raw weigh-in would swing the target by ~60 kcal overnight; the anchor holds still for seven days and steps down on its own. The target is shown under Metrics → Body with a button that writes it into `kcal_goal` (`POST /api/energy/target/apply`). It is also written on its own every Monday when `auto_kcal_goal` is on — off by default, switched on under Profile → Pace, and cleared with the pace, since without a pace there is nothing to compute. `CalorieTargetScheduler` runs daily at `Energy:RunAtLocal` (04:30, in `Hevy:TimeZone`) and brings a user up to date whenever `kcal_goal_updated_at` is older than this week's Monday, so a container that was down on Monday catches up on Tuesday rather than skipping the week.

- **How the day felt** — hunger and energy on a 1–5 scale, in their own `wellbeing_entries` table — was tracked and then removed: two numbers nobody read back. The table is dropped, the section is gone from Today, the day report has no "Befinden" block, and the free note it carried now comes off the body and sleep entries instead. The correlation block went with it: two of its four rows leaned on the removed numbers, and a block down to "sleep → volume" and "calories → weight" was not worth a card.
- **Workout history starts on 2026-08-17.** Sessions before it were deleted from the log once, and `Hevy:SyncFrom` keeps them from coming back.
- **The overview period is a calendar period**, not a trailing window (`periodRange` in `lib/period.ts`, unit tested). This week starts on Monday and this month on the first; only "6 months" and "1 year" trail from today, where no one thinks in boundaries. A trailing seven days reported five sessions for a week that had three, which is what this fixes. Each number is compared against the same number of days one period earlier — a Wednesday against last week up to its Wednesday — so the comparison is not a full week against a part of one. The overview is one card and no chart: sessions in the period, the daily means for sleep, calories and steps, the trend weight, and the mean macros as a `MacroSplit` (shares by calories, grams beside them) — the 7-day average at the end of the period against the one where it started, since a single morning swings by more than a week of eating does. The charts stay in the tabs that are about them.
- **The day's note has a row of its own** (`day_notes`, `GET/POST /api/notes`), and its own card at the bottom of Today. It was orphaned when `wellbeing_entries` was dropped, and it cannot live on the weight or sleep row: both refuse to save without a measurement, so a day that is only a sentence would have nowhere to go. Emptying it deletes the row rather than storing a blank. The day report reads it, and still reads the older per-entry notes so days written before this are not dropped.
- **Data export** (`GET /api/export/{area}?format=csv|json`, plus `all` for a JSON bundle that carries every area and the goals) exists because self-hosting is the argument for this app and `pg_dump` over SSH is a claim, not an export. Each area is declared once in `ExportController` as a header and a row shape, and both formats render from it, so a column cannot exist in one and not the other. CSV follows RFC 4180 and carries a BOM — without it Excel reads an umlaut in a note as mojibake. The bundle refuses CSV rather than flattening seven tables into a sheet. Offered under Profile as plain links: the response carries `Content-Disposition`, which is also the one path that works inside the installed app on a phone.
- **Notifications** are Web Push and nothing else — a PWA has no other channel. `PushService` sends through `Lib.Net.Http.WebPush`; the VAPID pair is configuration (`Push:VapidPublicKey` / `Push:VapidPrivateKey` / `Push:Subject`, generated once with `dotnet run --project backend -- vapid`), and without it `GET /api/push/config` reports `configured: false` and the frontend hides the whole card, exactly as the screenshot import does without a Gemini key. A row per browser (`push_devices`, unique on `endpoint`) rather than per user, because the same account is signed in on the phone and the desktop; a push service answering 404 or 410 retires that row, anything else is left alone. **On iOS this only exists once the app is on the home screen** — in a Safari tab the API is absent and the permission prompt does nothing, which is why `pushBlocker()` in `lib/push.ts` distinguishes "needs installing" from "cannot". The service worker is hand-written (`frontend/src/sw.ts`, VitePWA on `injectManifest`): Workbox's generated worker cannot hold a `push` listener, so the precaching it used to do for us is three lines at the top of ours.
- **What gets sent** is three things over that one channel, all off until asked for (`NotificationScheduler`, ticking every 5 minutes and covering the window since the last tick, so a slot is never delivered twice and a gap over 15 minutes is dropped rather than replayed): a **habit reminder** at `HabitSchedule.remind_at_local`, only on a day the habit is due *and* still open; an **evening check** at `Notifications:EveningCheckAtLocal` (21:00) only on a day with no nutrition and no weight row; and the **weekly review** Sunday at `Notifications:WeeklyReviewAtLocal` (20:00). The two account-wide ones are `notify_evening_check` / `notify_weekly_review` on `AppUser`; the habit one is per habit, set where the habit is edited. `HabitSchedules.IsScheduledOn` is shared between the overview and the reminder.
- **The weekly review** (`GET /api/summary/week/{date}/review`, `WeekReviewService`, `/week` in the app) is the week against the week before it: every number carries the same number from the previous week and the goal it is read against, and nothing else. No prose and no praise — the plain-text week log at `GET /api/summary/week/{date}` already says what happened and stays, for pasting elsewhere; what it could not say is whether the week was better than the last one. JSON rather than rendered text so the client says it in either language instead of a second German template in the backend. The weight line moves on the seven-day trend at each end of the week, never on two mornings.
- **Goals** live on `AppUser` (kcal, protein, water, steps, sleep minutes, target weight, weekly sessions and sets) and are edited under Profile. A goal that is set appears as the dashed line in the matching chart; an empty goal draws nothing.
- **The look is Apple's, at Apple's numbers.** `index.css` carries the system palette (grouped backgrounds, the label and fill ramps, systemBlue as the tint), the iOS text styles at phone sizes (12/14/17/20/24/30/36 — the step below read as a desktop app shrunk onto a phone), SF through `-apple-system` rather than a webfont, a 49 pt tab bar over blurred material, hairline separators at half a pixel, and a segmented control (`.segmented`) that both range switches use. Light and dark is a three-way choice — light, dark, or whatever the system is doing (`prefers-color-scheme`, followed live while the app is open) — stored as `jinsei:theme`, where 'system' is the absence of the key so the pre-paint script in `index.html` and `ThemeProvider` read one meaning. `theme-color` is a single tag written by both, not a pair keyed on the media query: an explicitly light app on a dark phone would otherwise get a black bar over a white page. Colour is the only thing a **palette** changes: `data-theme` on `<html>` selects one of four (`lib/palettes.ts` — system, jinsei, rosepine, catppuccin), each bringing its own light and dark halves, chosen under Profile and stamped in `index.html` before the first paint so the wrong one never flashes. Light/dark stays a separate axis. Anything a palette must be able to recolour has to be a token — `--thumb` exists because a hard-coded white slider thumb survived the first attempt.
- **Dashboard widgets** are chosen and ordered in the browser (`lib/dashboardWidgets.ts`, localStorage) — deliberately not synced through the API.
- **Screenshot import** (`POST /api/import/screenshot`) reads a Sleep Cycle screenshot with the Gemini API (`GeminiClient`, free-tier Flash model) and returns a *draft* — it never writes. The sleep prompt reads the newer Sleep Cycle log screen: the two clock times off the axis under the phase curve and the four phase durations out of its legend, and it is told to ignore every score and percentage on that screen. The client fills the normal form with it and the night still goes through the sleep upsert on confirm, which is what turns the times into a duration and the phases into the slept total. The draft box under the button says nothing when there is nothing to say: the fields fill in visibly, so it only appears for a guessed field, a dropped value, a screenshot from another day, or the model's own note. The endpoint still understands `kind: "nutrition"` and FatSecret, but the nutrition form no longer offers it — four numbers are typed faster than they are photographed. Needs `Gemini:ApiKey`; without it `GET /api/import/status` reports `configured: false` and the frontend hides the button.
